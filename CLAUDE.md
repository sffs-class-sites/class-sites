## 1. Architecture (decided)

**Content lives in this repo, is built by GitHub Actions, and is served by GitHub Pages.** Each shared embed is placed in a Google Site once with **Insert → Embed → By URL → Whole page**. After that, repo changes reach every site within ~10 minutes (Pages sends `cache-control: max-age=600`) with no Sites edit and no republish.

**A site follows a class, not a grade.** Families keep one URL for nine years. Embed URLs name the class (`…/academics/?class=2034`) and the embed works out the grade at view time: `grade = 8 - (gradYear - schoolYearEndYear)`, rolling over on the **last day of school** (Ahin, 2026-10-30; replaces "August 1"). A `?grade=N` override exists for previewing next year. Because the class is in the URL, **nothing in Google Sites changes at rollover**.

*Built 2026-10-31:* `shared/class/class.js` is the model (inlined into every shared embed by `build/classinfo.py`, which mirrors it in Python for builds and tests), and `shared/school-years.json` holds each year's first and last day. **Add next year's row there when the school publishes its calendar**; until then the embeds assume the year ends June 30. Kindergarten is grade 0; before K the class is "not yet at SFFS", after 8th "graduated". The live embeds are still placed without `?class=` (one calendar for every grade); they get `?class=` when per-class filtering exists (`docs/ROADMAP.md` D3), so the Sites edit happens once.

**Repo is public and stays public.** Considered and rejected going private: Pages from a private repo needs a paid plan, Actions minutes stop being free (unlimited for public repos; 2,000/month on Free, 3,000 on Team for private), and the published site is public either way. Private would protect history, not the page.

**Never transfer the repo.** GitHub redirects repository URLs after a transfer but *not* Pages URLs, which would break every embed. Ownership moves by adding/removing org owners.

## 2. Data sources and the content map

Humans author in Google Docs and Sheets. A `Site Map` sheet (authored by Ahin) is the index; the repo keeps a generated copy that agents read. Per source it records:

- **Drive file ID** (not a path — IDs survive renames and moves)
- **Shape**: one Doc split by grade headings, one file per grade, or a Sheet with a row/tab per grade
- **Key**: `grade` (academics), `school-year` (Important Dates), or `class` (room parents, teachers)
- **Publish list**: the exact columns or sections allowed on the site, plus who approved and when

**Fail closed.** Anything not on the publish list is never published, including newly added columns. Removing an entry removes it from the sites on the next sync.

## 3. Personal data: pattern A now, pattern B next school year

"Approved for the website" (the school's OK, recorded in the publish list) is not the same as "fine in permanent git history". So:

- **Non-personal content** (dates, academics, school hours) → data files in this repo, normal PR review.
- **Approved personal content** (room parent name/email, later student first names by class) → **never committed**. The master sheet is restricted to authorized accounts; a scheduled job signed in as the bot identity reads only the publish-list columns and writes a small extract that the embed fetches at view time.

**No personal data on the public sites at all (Ahin, 2026-11-11), school approval or not.** Room-parent names and emails come off the 1st-grade site. Contact lists live in each grade's own Class Sheet (public, anyone-with-link, kept by the room parents), and **Ahin types the Class Sheet link into each Site by hand** where needed; no embed replaces Room Parents (Ahin, 2026-11-11, aware that a hand-typed link is unmonitored and can drift). Personal content on a Site waits for pattern B. The room-parents pipeline is dormant, not deleted (§7). The per-class Class Sheet URLs and tabs, each grade's WhatsApp invite link (a secret: never on a site, never in this repo) and room-parent contacts are recorded only in the restricted **admin sheet** (identities table below), whose **Setup inventory** tab also lists everything that lives on a non-school account so it can move to the school account later.

**One exception (Ahin, 2026-11-12):** the Drop-off & Pickup embed names the two staff contacts for Middle School self-dismissal, as the school's own document does. Names only, no email or phone; it is in `shared/dropoff-pickup/data.json`, so it is in git. It is an exception for that card, not a change to the rule.

**Pattern A (now):** restricted master sheet → published extract → public embed. Protects the master file and its extra columns; the displayed data is public, which matches today's public sites.

**Pattern B (next school year):** viewer must be signed in. Needs a Google Apps Script layer deployed to the school domain. Measured costs from earlier testing: 0.6–3.5s to load versus ~20ms for Pages, and one failure in ~16 loads. Required before publishing anything that must not be public, e.g. class lists. **Build A so the switch to B is a swap of the data source, not a rewrite:** keep fetching, rendering and formatting separate, and keep the data contract (the JSON shape) stable.

## 4. Change control

- A push to `main` publishes to every live site. `main` is production: all changes go through a pull request.
- `main` is protected by the ruleset **protect main** (id 24882477, active since 2026-10-11): require a PR (0 approvals), require the `build` check from GitHub Actions, block force-push and deletion, no bypass actors. Required approvals stay at 0: **there is no second maintainer, by choice** (Ahin, 2026-10-30; accepted risk). Everything here assumes no second reviewer, so CI is the gate. GitHub won't let an author approve their own PR, so raising approvals would block Ahin.
- A direct push to `main` is refused with `GH013: Repository rule violations` ("Changes must be made through a pull request", "Required status check \"build\" is expected"). Tested 2026-10-11.
- `SFQuakerBot` (the GitHub account Claude sessions use) was an org owner during setup and is an **org member with write access** since 2026-10-31 (§9 item 11). It can open, push to and merge PRs but cannot change rulesets, repo settings, secrets or org membership; those are `Ahin-SFFS`'s alone.
- The ruleset has no bypass actors, so the bot **cannot** push past it (verified 2026-10-11 while it was still an owner). No session should change rulesets, branch settings or org membership without Ahin asking for it in that session; since the demotion the bot cannot anyway.
- Every PR must be reviewable without reading code: CI posts desktop + phone screenshots and a plain-English summary (events added/changed/removed).
- **Who merges** (§0 item 12): content PRs from the approval pipeline are merged by the bot once CI passes; the room parent's approval, linked in the PR, is the human review. The repo's auto-merge setting is off, so the job merges explicitly (`deploy.yml` `automerge`, as SFQuakerBot): the `email-log-auto` and `updates-auto` branches since 2026-11-05, and **since 2026-11-06 every PR opened by SFQuakerBot or carrying Claude Code's footer, code, workflows and instructions included** (Ahin's decision: full automation; CI is the gate, the deploy email is the review, rollback is a revert of the PR). Ahin merges nothing by default. A PR from a fork never auto-merges. Turning the repo setting on instead is Ahin's call (§4 residual risk).
- **Why merging happens in Actions and not in a session:** Claude Code's own permission check refuses `gh pr merge` and `git push -f` inside sessions, cloud routines included, and it cannot be turned off for routines. A session opens the PR; GitHub merges it. Sessions therefore never force-push; a branch that still exists is an open PR to build on.
- **What still needs Ahin's hands:** the ruleset, repo settings, secrets and org membership (SFQuakerBot cannot change them, §9 item 11); placing an embed in Google Sites (no API); sharing anything in Drive the bot is not on; and the Claude-side setup of routines and connectors.
- **Updates pipeline publishes without a review step (Ahin, 2026-11-05):** the email-log index and the extraction routine's ledger changes merge on a green build and deploy; `deploy.yml`'s `notify` job then emails Ahin what changed (`build/notify_changes.py`, to the `UPDATES_NOTIFY_TO` variable, from the bot's Gmail). That email is the review; a correction is a follow-up PR. Since 2026-11-06 any other deploy (code, workflows, docs) sends its own email with the PR's title, summary and files (`build/notify_deploy.py`).
- Rollback = revert the merge commit.

**Sheet-sourced personal data has its own approval, in the sheet:**

1. People edit a **Draft** tab. The sites read a protected **Live** tab, so half-finished edits never appear.
2. A **Publish** menu item (Apps Script) validates first: required columns, email format, known class year, no blank names, row count sanity.
3. On success it copies Draft → Live, writes date/who/what to a **Log** tab, and keeps the previous version in **History** for one-click revert.
4. Sites show the change within a few minutes (Google's published-file cache; exact duration untested).

## 5. Rules learned the hard way

- Google Sites' iframe sandbox is `allow-scripts allow-popups allow-forms allow-same-origin allow-popups-to-escape-sandbox allow-downloads allow-storage-access-by-user-activation` — **no top-level navigation**. Filters, month jumps and tabs must be `<button>` + JS (they work in place). Outbound links need `target="_blank" rel="noopener"`. Never `href="#…"`: it opened new windows on iOS Chrome.
- Embeds fill their frame: `html,body{height:100%}`, one scroll container, scroll-hint pill. Anything that auto-scrolls on load must retry — Sites lays the iframe out late.
- Sites sizes a published embed by the editor box's **shape**, not a scale factor: width = the content column (max 1154px, from a ≥1280px window; 905px at 1024), height = width × box h ÷ w. Phones keep the same shape, so a wide box is a letterbox on a phone: Important Dates is 352 × 206 on an iPhone 13. Measured 2026-10-11 (§0 item 1).
- **One standard box (2026-11-02).** Every slot is placed at the `card` box in `registry.yaml` `boxes` (935 × 625 in the editor, h ÷ w 0.668: 1154 × 770 on a desktop, 352 × 235 on an iPhone 13). `page` (935 × 875) is only for an embed that is the only thing on its page (Key School Systems and Drop-off & Pickup, on the 1st-grade site since 2026-11-12; Updates was one until 2026-11-11, when it moved to the 1st-grade Home at `card` and its Email Digest page was deleted). Every shared embed must be usable at `card` on a phone, and its CI check renders it at 352 × 235 and 315 × 210 (`render_check.py`, `updates_check.py`, `room_parents_check.py`), so nobody tunes a box per embed and a new slot is always the same drag. Updates got a one-line phone header for this. The daily live check lists any live box whose shape is off its registry box, without alerting.
- **Every embed opens at the top, title first** (Ahin, 2026-11-11; Important Dates used to scroll to its filter bar on load, which hid the header). Important Dates on a phone shows the next three dates without scrolling at the `card` box on an iPhone 13 (352 × 235), and at least two on the narrowest phones (315 × 210), where the title line costs one date on the busiest days: at 560px and below its header is one line, the title and an **Options** button that unfolds the subhead, PDF link, add-all and calendar chooser. Below 400px the embed switches to a compact layout (one line per date, category as a coloured edge, badge and details on tap, a "Full page" link), so that needs a box with **h ÷ w ≥ 0.67** (worst day of the year, 315px phone, measured 2026-10-31; it was 0.95 before the compact layout). `tests/render_check.py` fails CI if a 315 × 210 frame shows fewer than three on any day, and checks tap-target size, text size, the tap-to-open details and the full-page link at phone widths. Recommended editor box: 935 × 625.
- **Translation (2026-11-02):** every embed is English with `lang="en"`, so browsers offer their own translation, and every build inlines `shared/lang/translate.js`: when the browser's first language is not English, a one-line notice in that language links to the same page through Google Translate in a new tab (dismissable, remembered per browser). `tests/lang_check.py` checks it in all three browser checks. New embeds must inline it too (`classinfo.lang_js()`).
- **House style: a capital letter after a colon (Ahin, 2026-11-12).** "Tuition and fees: Every SFFS bill …", never "…: every …". One rule in `build/style.py`, enforced three ways: each embed's data check refuses our own wording that breaks it (`validate_updates.py`, `validate_important_dates.py`, and the School Hours, Team Schedule and Key School Systems builds); fields the page prints after a colon of its own ("Drop-off: " + text, "Due Oct 28: " + what) must start with a capital; and `tests/style_check.py` opens every built embed in CI and reads all its text, so template wording is held to it too. Exempt: text quoted from elsewhere, such as an email's subject line in the Updates ledger (the build links to the email by that exact subject), and times and links. Text that only appears after a click (a calendar choice) is not seen by the rendered check, so keep template strings to the rule by hand.
- **No API exists for current Google Sites.** Placing an embed is manual; content changes never are. **Resizing a box and publishing are scripts, not sessions clicking through the editor:** `tools/sites_editor.py` (`list`, `resize`, `publish`, `restore` for the Version-history rollback; `docs/sites-editor-driver.md`) attaches to a Chrome on the Mini signed in as `classpages@` with remote debugging on; `python3 tools/sites_editor.py chrome` starts that Chrome (maximised, right data dir, port open) and asks a person to sign in once if the data dir isn't yet. It runs only from a session on the Mini (Remote Control or the desktop app), never from a cloud session, and every write needs `--apply`. First real resize 2026-11-02 (1st-grade room-parents box); rollback and the publish dialog tested 2026-11-06 with no visible change. On the Mini, Claude Code's auto-mode classifier refuses these writes unless `~/.claude/settings.json` allows `python3 /Users/thomasfamilybot/Documents/sffs/class-sites/tools/sites_editor.py *`, so run the script from that clone by its full path. **The Mini's only clone is `~/Documents/sffs/class-sites`** (the `~/code/sffs/class-sites` clone the rule first named was deleted 2026-11-07; the rule must be updated to match, by hand on the Mini). The editor shows **no size label** on a selected embed; the script measures the iframe instead, so never ask a person to "drag until the label reads 935 × 625".
- **The Claude Google connectors see less than their account does (2026-11-11).** The Drive and Sheets connectors open a file only if the Claude app created it or it is shared **directly** with the connector's account; a sheet inside a folder the connector's account does not own is "permission denied" / "not found" even when shared directly and even to the folder's owner, and moving a working sheet into such a folder breaks it (tested with bot-owned and Ahin-owned sheets in the bot's admin folder). So a sheet a session must write lives in a My Drive root and is shared with `thomasfamilybot@gmail.com` directly; folders hold shortcuts. Creating a file *as the bot* is done in Claude in Chrome's profile, where the bot is `authuser=7` (`/u/7/`), never by assuming an index: that profile has eight accounts, family members' among them.
- Claude in Chrome cannot click inside a cross-origin iframe on a published Site, and screenshot-by-screenshot browser automation is expensive; that is what the editor driver above replaces. Use Playwright in GitHub Actions (it can reach sites.google.com) for live-site checks; `tests/live_check.py --site <key>` also runs from a cloud session or the Mini. A human does a 2-minute desktop + iPhone check per new embed type.
- .ics UIDs must never change for an existing event or families' re-imports duplicate. Each event's `uid` is stored in `data.json` and never recomputed. The 2026–27 values were frozen from the old derivation `<date>-<slug(title)>@sffs-calendar` (+`-2` for duplicates) and match the live pasted embeds; a new event gets its uid once, at approval.

## 6. Decisions from Ahin's dates-pipeline work

- Store `uid` explicitly per event, assigned once, never recomputed from the title. Done for 2026–27 (2026-10-11): frozen into `data.json`, and the build reads them.
- Schoolwide events are one shared record with per-grade additions. `audience` = grouping key or grade list (Lower School K–4, Middle School 5–8); the resolved list is snapshotted at approval.
- Optional `start_time`/`end_time` (absent = all-day). When timing arrives, the all-day event is replaced by a timed event with a new UID.
- Per-event calendar adds are one-time copies. A subscribed .ics feed is deferred: dropping a UID from a feed deletes it from subscribers' calendars.
- Email ingestion and per-grade approval queues are designed, not built.
